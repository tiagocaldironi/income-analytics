# Purpose

The Canonical Financial Event Model (CFEM) defines the official financial event model used throughout the Income Analytics platform.

Every external integration (banks, brokers, exchanges, custodians, CSV files, APIs, etc.) must transform its proprietary representation into this canonical model before any business processing occurs.

The CFEM acts as the language shared by every module of the system.

# Design Principles

## 1. Event First

The system stores **facts**, never derived state.

Examples of facts:

- Buy Asset
- Sell Asset
- Receive Dividend
- Receive Interest
- Deposit Cash
- Withdraw Cash

The system **does not persist**:

- Portfolio Position
- Average Price
- Net Worth
- Performance
- Passive Income
- Profit & Loss

Everything is reconstructed from events.

---

## 2. Immutable Ledger

A Financial Event represents a historical fact.

Once created:

- It is never modified.
- It is never deleted.

Corrections are performed through new events.

Example:

```
BUY PETR4
100 shares

↓

REVERSAL

↓

BUY PETR4
90 shares
```

This guarantees complete auditability.

---

## 3. Canonical Representation

Regardless of the data source:

- Nubank
- XP
- BTG
- B3
- Interactive Brokers
- Binance
- CSV
- OFX

Every record must become a FinancialEvent.

---

## 4. Explainability

Every number presented by the system must be traceable back to one or more Financial Events.

The system should always be capable of answering questions such as:

- Why did my portfolio increase this month?
- Which event changed my average price?
- Which dividends compose my passive income?
- Which operations generated taxes?

# Financial Event Lifecycle

Every Financial Event follows the lifecycle below.

```
Imported
     │
     ▼
Validated
     │
     ▼
Canonicalized
     │
     ▼
Processed
     │
     ▼
Available for Analytics
```

## Imported

Raw event received from an external source.

## Validated

Basic validations were executed.

Examples:

- mandatory fields
- duplicated event
- invalid asset

## Canonicalized

The event has been transformed into the CFEM.

At this point every source speaks exactly the same language.

## Processed

Business engines have consumed the event.

Examples:

- Position Engine
- Income Engine
- Snapshot Engine

## Available for Analytics

The event is ready to answer user queries.

# Architectural Rules

## Rule 1

Every Financial Event belongs to exactly one Account.

---

## Rule 2

Every Financial Event may reference one Asset.

Cash-only events do not require an Asset.

---

## Rule 3

Financial Events are immutable.

---

## Rule 4

Derived information is never persisted.

Examples:

- Position
- Average Cost
- Net Worth
- Performance
- Passive Income

---

## Rule 5

Business engines consume only Financial Events.

They never access proprietary import formats.

---

## Rule 6

Import adapters are responsible for translating external formats into the Canonical Model.

# ADR-005

## Decision

Income Analytics adopts the Canonical Financial Event Model (CFEM) as the official representation of every financial fact.

Every calculation performed by the system is derived exclusively from the event history.

---

## Consequences

### Advantages

- Complete auditability
- Explainable calculations
- Historical reconstruction
- Source independence
- Easy integration with new brokers
- Event replay capability
- Scalable architecture

### Trade-offs

- Event processing is more complex.
- Historical reconstruction requires processing event streams.
- Derived data may require optimization strategies (snapshots) in the future.
