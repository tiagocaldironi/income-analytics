# Purpose

This document defines the Aggregate Roots of the Income Analytics domain.

Aggregates establish transactional consistency boundaries and define which objects are responsible for enforcing business invariants.

Every modification to the financial domain must occur through an Aggregate Root.

---

# What is an Aggregate?

An Aggregate is a cluster of domain objects treated as a single consistency boundary.

Only the Aggregate Root can be referenced from outside the Aggregate.

All modifications must occur through the Aggregate Root.

# Aggregate 1

# Financial Ledger

## Aggregate Root

FinancialLedger

---

## Responsibilities

The Financial Ledger is responsible for:

- Preserving the event stream
- Maintaining chronological consistency
- Preventing duplicate events
- Preserving immutability
- Providing deterministic replay

---

## Contains

```
FinancialLedger

├── FinancialEvent

├── FinancialEvent

├── FinancialEvent

└── FinancialEvent
```

---

## Business Invariants

The Ledger guarantees:

- Events cannot be modified.
- Events cannot be deleted.
- Events belong to exactly one Account.
- Events are processed in deterministic order.
- Duplicate events are rejected.

---

## Public Operations

Examples:

```
append_event()

replay()

events()

contains()

last_event()

event_count()
```

Business engines never modify Ledger contents.

# Aggregate 2

# Account

## Aggregate Root

Account

---

## Responsibilities

Represents an investment account maintained by a financial institution.

Examples:

- XP
- Nubank
- BTG
- Interactive Brokers

The Account owns exactly one Financial Ledger.

---

## Contains

```
Account

↓

Financial Ledger
```

---

## Responsibilities

- Account identification
- Institution relationship
- Currency
- Account status

It does **not** calculate investment positions.

# Aggregate Communication

Aggregates never modify one another directly.

Communication occurs through:

- Financial Events
- Domain Services
- Application Services

---

# Transaction Boundaries

A transaction should modify only one Aggregate whenever possible.

Examples:

✅ Append Financial Event

✅ Create Account

✅ Register Asset

Avoid:

❌ Updating multiple Aggregates in a single business transaction.

# Design Principles

- Small Aggregates
- High Cohesion
- Low Coupling
- Immutable Financial History
- Explicit Transaction Boundaries
- Replayable Domain

---

# ADR-009

## Decision

Income Analytics adopts small, focused Aggregates.

The Financial Ledger is the central Aggregate Root of the financial domain.

Master Data entities are independent aggregates.

Portfolio and Position are Read Models, not Aggregates.
